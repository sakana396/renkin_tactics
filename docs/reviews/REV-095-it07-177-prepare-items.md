## 検証

- Issue #170 と PR の説明、`git diff origin/main...HEAD` を照合した。次の点は設計どおりである
  - 準備の「名簿」「持ち物」のタブ、名簿・持ち物の左列と右列、常に 5 行の枠（空きは「―」、先頭の武器に E 印）、武器・杖・道具の見出しで分けた在庫
  - 出し入れは既存の core の操作（TakeItem・StoreItem・TakeWeapon・StoreWeapon・MoveWeaponFirst）を呼ぶ。失敗では Campaign を変えない（追加のテストはセーブの中身のバイト列を操作の前後で比べる）
  - 取消しの段階、配置への遷移。巻き戻しの処理は変えていない。準備から配置を経て戦闘を始めるケースがある
- TC-FR-CMP-03-16・17 は TST-IT07、テストコード、traceability の FR-CMP-03 の行で一致する。既存のケースの改訂は、TST-IT07 1 章の #170 の影響範囲とおおむね一致する
- 期待値は主に DES-IT07 3.5 節の座標と既存の操作から導かれている
- レビューの時点では、画面のテストの入力の経路（F-02）と長い品名の検出力（F-03）が残っていた。PR の説明の「ミュータント 17 個を検出」と撮影の結果は、レビューでは再実行していない
- レビューの環境（読み取り専用）では `gofmt -l .` は出力なし。`GOOS=windows go vet ./...` と `go run ./tools/tccheck` は作業用ディレクトリを作れず、レビューでは未検証。CI は未確認
- 対応後（43b985e と、その後の origin/main の取り込み）に実装者が確かめた結果: `gofmt -l .` は出力なし、`GOOS=windows go vet ./...` は指摘なし、`internal/ui` のテストの実行ファイル（Windows 向け、WSL から実行）は PASS、core・tactics・defload・savefile・tools の `go test` は ok、`go run ./tools/tccheck` は OK。追加のミュータント 3 個（品名を縮めない、場面の入力で左クリック・Tab を渡さない）も検出し、合計 20 個
